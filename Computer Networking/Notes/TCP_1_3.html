0. Big picture

The network layer (IP) delivers packets host to host. The transport layer delivers data process to process (app to app) — that’s “logical communication”.

Example: two apartment buildingsBuilding A and B each have 12 kids who write letters to each other. The postman (IP) only brings mail to the building. In each building, one kid (the transport layer) collects outgoing letters and hands incoming letters to the right kid. Kids = processes, building = host, kid-in-charge = transport protocol.
  • Sender: takes the app message → cuts it into segments (adds a transport header) → hands to IP.
  • Receiver: gets segments from IP → checks the header → rebuilds the message → gives it to the right app via a socket.

Neither can promise delay or bandwidth guarantees.

1. Multiplexing & demultiplexing

  • Multiplexing (sender): collect data from many sockets, stick a header (with ports) on each.
  • Demultiplexing (receiver): read the header and push each segment to the correct socket.

Every segment starts with source port and destination port (16 bits each). Every IP datagram carries source/destination IP. The host uses IP + port to find the socket.

ProtocolSocket is found using
UDPDestination port only
TCP4-tuple: source IP, source port, dest IP, dest port
Example: web server on port 80Two browser tabs (clients C1, C2) connect to one server, both to dest port 80.
UDP: both would land in the same socket (same dest port).
TCP: the 4-tuples differ (different source IP/port), so the server makes a separate socket per client.
RememberUDP = 1 key (dest port). TCP = 4 keys (the 4-tuple).

2. UDP — “send and hope”

A bare-bones protocol. Segments may be lost or arrive out of order. Each segment is handled alone.

Why would anyone use it?

  • No handshake → no extra RTT delay.
  • No connection state kept at sender/receiver → simple.
  • Small header.
  • No congestion control → can blast at any speed, even when the network is jammed.

Used by: streaming/video calls (loss-tolerant, rate-sensitive), DNS, SNMP, HTTP/3. If you need reliability on UDP, build it in the application (HTTP/3 does).

UDP header (4 fields × 16 bits = 8 bytes)

source port | dest port | length | checksum then the data. Length = whole segment incl. header, in bytes.

Internet checksum (detects flipped bits)

Sender treats the segment as 16-bit numbers, adds them, and stores the result in the checksum field. Receiver recomputes and compares.

Maths one-linerAdd normally. If a 1 “falls off” the left end (carry-out), add it back at the right (wraparound). Then flip every bit → that’s the checksum.
Worked example1110011001100110 (= E666)
1101010101010101 (= D555)
Sum = 1 1011101110111011 → carry out! Add 1 back → 1011101110111100
Flip all bits → checksum = 0100010001000011
Receiver adds all pieces plus checksum: if no error, you get all 1s.

Weak protection: if one bit flips 0→1 in one number and another flips 1→0 in the same column of another number, the sum stays the same → error goes undetected.

3. Principles of reliable data transfer (rdt)

Goal: give the app a reliable channel while the real channel below is unreliable. Sender and receiver can’t see each other’s state — they only learn by messages (ACKs).

Functions: rdt_send() (app → rdt), udt_send() (rdt → unreliable channel), rdt_rcv() (packet arrives), deliver_data() (rdt → app). We study one-way data, but ACKs flow both ways. Designs are written as finite state machines: state → event / actions → next state.

The ladder: each version fixes one problem

rdt2.2Same, but NAK-freeACK carries the seq # of the last good packet; a duplicate ACK = NAK (TCP does this)

RememberError → checksum. Bad feedback → seq #. Loss → timer. Duplicates from timers → seq # kills them.

Stop-and-wait: send one packet, wait for its ACK. If the ACK is just late, the retransmit is a duplicate, and the seq # handles it.

▶ rdt3.0 in action (packet loss, then ACK loss)

Why stop-and-wait is terrible

Worked example: 1 Gbps link, 15 ms one-way delay, 8000-bit packetTransmit time: L/R = 8000 / 10⁹ = 8 µs = 0.008 ms
RTT = 2 × 15 = 30 ms
Utilization U = (L/R) / (RTT + L/R) = 0.008 / 30.008 ≈ 0.00027
The sender is busy only 0.027% of the time. The protocol wastes the fast link. Fix: pipelining.

Pipelining: send many packets before waiting for ACKs. Needs a larger seq # range and buffering. 3 packets in flight → utilization ×3.

Go-Back-N (GBN)

  • Sender has a window of up to N unACKed packets. Uses cumulative ACK: ACK(n) = “everything up to n received”. Window slides to start at n+1.
  • One timer (for the oldest unACKed packet). On timeout(n): resend n and every later packet in the window.
  • Receiver remembers only rcv_base. Out-of-order packet → discard (or buffer, implementer’s choice) and re-ACK the highest in-order seq #. This creates duplicate ACKs.
▶ Go-Back-N: pkt2 lost

Selective Repeat (SR)

  • Receiver ACKs every correct packet individually and buffers out-of-order ones; delivers to the app in order once the gap fills.
  • Sender keeps a timer per packet; on timeout resends only that one. Window advances when the smallest unACKed packet is ACKed.
  • Receiver: packet in [rcvbase, rcvbase+N−1] → ACK it. Packet in [rcvbase−N, rcvbase−1] (already delivered, ACK was lost) → ACK again. Otherwise ignore.

The SR dilemmaSeq #s 0,1,2,3 and window 3. Sender sends 0,1,2; all ACKs are lost; sender times out and resends 0. The receiver, already expecting a new seq 0 next, accepts the resend as new data → duplicate delivered. The receiver can’t see the sender, so both cases look identical.
Rule: sequence-number space must be at least 2 × window size.

4. TCP

Point-to-point (1 sender, 1 receiver) · connection-oriented · reliable in-order byte stream (no message boundaries) · full duplex · cumulative ACKs · pipelined (window set by flow + congestion control) · MSS = max segment size.

Example: telnet, user types ‘C’A → B: Seq=42, ACK=79, data='C'
B → A: Seq=79, ACK=43, data='C' (ACKs the C, echoes it back)
A → B: Seq=43, ACK=80 (ACKs the echo)
Rule: ACK = my seq + bytes received. 42 + 1 byte = 43.

Timeout: how long to wait?

Too short → needless retransmits. Too long → slow reaction to loss. So estimate the RTT. SampleRTT = time from sending to ACK (ignore retransmitted segments). Smooth it with an EWMA (recent samples matter more, old ones fade exponentially):

EstimatedRTT = (1−α)·EstimatedRTT + α·SampleRTT, α = 0.125
DevRTT = (1−β)·DevRTT + β·|SampleRTT − EstimatedRTT|, β = 0.25
TimeoutInterval = EstimatedRTT + 4·DevRTT (the 4·Dev is the safety margin; more jitter → bigger margin)

Maths one-linerα = 0.125 = 1/8 → “keep 7/8 of the old value, add 1/8 of the new sample”. β = 0.25 → “keep 3/4 old, add 1/4 new”.
Worked example (slides): start EstimatedRTT = 370, DevRTT = 45, samples 380, 390, 340 ms (The samples are worked backwards from the slide’s answers.)
Round 1: Est = 0.875×370 + 0.125×380 = 323.75 + 47.5 = 371.25
Dev = 0.75×45 + 0.25×|380−370| = 33.75 + 2.5 = 36.25 (uses the old estimate)
Timeout = 371.25 + 4×36.25 = 516.25

Reliable transfer in TCP (a GBN/SR hybrid)

  • Sender: data from app → make segment, start timer if not running (timer = oldest unACKed segment). Timeout → resend that segment, restart timer. ACK → update what’s ACKed; restart timer if anything is still unACKed.
  • Out-of-order handling at the receiver is left to the implementer.

Retransmission scenariosLost ACK: A sends Seq=92 (8 bytes → 92–99); B’s ACK=100 is lost; A times out, resends Seq=92; B sees a duplicate, discards, re-ACKs 100.
Premature timeout: A sends Seq=92 (8 B) and Seq=100 (20 B); ACKs 100 and 120 are slow; A resends 92; B replies with cumulative ACK=120 and the sender moves on. Only one segment is resent.
Cumulative ACK saves you: ACK=100 is lost but ACK=120 arrives in time → covers both, no retransmit.
Fast retransmitSegment 100 is lost, but later segments arrive, so B keeps sending ACK=100 (duplicates). 3 extra ACKs for the same data (triple duplicate ACK) = “3 segments arrived after the hole, it’s probably lost” → resend the smallest unACKed segment now, without waiting for the timeout.

Flow control (protect the receiver)

If IP delivers data faster than the app reads it, the receive buffer overflows. The receiver advertises free space in rwnd:

rwnd = RcvBuffer − (data sitting in buffer). Sender keeps unACKed bytes ≤ rwnd → buffer can never overflow.

Example (water tank)RcvBuffer = 4096 bytes, 1000 bytes not yet read by the app → rwnd = 3096. The sender may have at most 3096 unACKed bytes in flight. As the app reads, rwnd grows again.

Silly Window Syndrome: tiny segments (e.g. 1 byte of data + 20 bytes of header!) waste the network. Two causes, two fixes:

  • Slow sender → Nagle’s algorithm: send the first bytes right away; then wait until enough bytes accumulate (≈ a full segment) or the ACK for the earlier data arrives; repeat.
  • Slow receiving app → Clark’s solution: don’t advertise tiny windows. Either delay the ACK until enough buffer is free, or ACK at once but advertise rwnd = 0 until a reasonable amount of space opens.

Connection management

Before data, both sides agree to connect and exchange starting seq #s and buffer sizes (state = ESTAB).

Why not a 2-way handshake? Delays, retransmitted requests and reordering break it: (1) half-open connection — client dies but server thinks it’s connected (an old duplicate request re-opened it); (2) duplicate data accepted — an old retransmitted request plus old data gets accepted as new.

3-way handshake fixes this: SYN → SYNACK → ACK. The client’s random start seq x and the server’s y must each be acknowledged, proving both are alive.

▶ TCP 3-way handshake

Client states: LISTEN (server only) → SYNSENT → ESTAB. Server: LISTEN → SYN RCVD → ESTAB. The 3rd segment may already carry data.

Closing: each side sends a segment with FIN=1; the other answers with an ACK (which can be combined with its own FIN). Simultaneous FINs are fine.

5. Congestion control

Congestion = too many senders sending too fast for the network. Symptoms: long delays (router queues) and packet loss (buffer overflow).

Flow controlCongestion control
One sender too fast for one receiverMany senders too fast for the network

Costs of congestion (3 scenarios)

ScenarioWhat happens
1: two senders, one router, infinite bufferMax throughput per connection = R/2. Delay grows huge as the send rate nears R/2.
2: finite buffer, retransmissionsPackets get dropped → resent. Real senders also time out early, sending unneeded duplicates. Link carries extra copies, so useful throughput drops.
3: four senders, multi-hopA packet dropped far along the path wastes all upstream capacity already spent on it. Throughput can fall toward 0.

Insights: delay climbs near capacity · loss + retransmission cut effective throughput · duplicates cut it more · throughput can never exceed capacity · downstream drops waste upstream work.

Two approaches: end-to-end (no help from routers; guess from loss/delay — TCP does this) or network-assisted (routers give feedback, e.g. ECN).

TCP congestion control

The sender limits itself with cwnd: LastByteSent − LastByteAcked < cwnd. Roughly: send cwnd bytes, wait one RTT, send more, so rate ≈ cwnd / RTT bytes/s. (Real window = min(cwnd, rwnd).)

Maths one-linerRate = window ÷ RTT. cwnd = 10 MSS, MSS = 1000 B, RTT = 0.1 s → 10,000 B ÷ 0.1 s = 100,000 B/s.

AIMD: “probe, crash, back off”

Additive Increase: +1 MSS per RTT until loss. Multiplicative Decrease: cut on loss. Drawn over time it’s a sawtooth. It’s distributed, stable and optimises flow rates network-wide.

Three phases

  1. Slow start: cwnd = 1 MSS, doubles each RTT (+1 MSS per ACK). Starts slow, ramps up exponentially.
  2. Congestion avoidance: once cwnd > ssthresh, grow only +1 MSS per RTT (linear). On loss, ssthresh = cwnd/2 (half the cwnd just before loss).
  3. Loss reactions: 3 duplicate ACKs (mild) → TCP Reno: ssthresh = cwnd/2, cwnd = ssthresh (+3), fast recovery, then congestion avoidance. Timeout (severe) → ssthresh = cwnd/2, cwnd = 1 MSS, back to slow start. (Old TCP Tahoe cut to 1 MSS on both.)
RememberDup ACKs = network still delivers something → halve. Timeout = nothing gets through → restart from 1.
▶ cwnd over time (Reno), one point per RTT, ssthresh starts at 8

Reading it: 1→2→4→8 slow start (×2) · 8→12 linear (+1) · 3 dup ACKs: 12→6 · 6→12 linear · timeout: 12→1, then 1,2,4,6 doubling until ssthresh (=6), then +1.

Beyond classic Reno

  • TCP CUBIC: remembers Wmax (rate where loss occurred). After the cut, ramps up fast when far from Wmax, slowly and carefully near it (window grows with the cube of time distance from K). Linux default; most popular for web servers (until ~2024).
  • Bottleneck link idea: the slowest link on the path is always busy; its queue is rarely empty. Raising send rate there gives no extra throughput, only more queueing delay (higher RTT). Goal: “keep the pipe just full, but not fuller.” Ideal in-flight data = bandwidth × min RTT (bandwidth-delay product).
  • Delay-based / BBR: loss-based TCP runs at the full-buffer point; BBR runs at the just-full point, adjusting in-flight data (acceleration → cruising → deceleration to re-measure min RTT). Used on Google’s internal backbone.
  • ECN (network-assisted): a router sets 2 bits in the IP header (ToS) when congested; the receiver sets the ECE bit in its ACK; the sender slows down — no packet loss needed.

Fairness

Goal: K TCP connections sharing a bottleneck of rate R each get R/K. AIMD achieves this (idealised: same RTT, all in congestion avoidance) because additive increase moves both equally while halving hurts the bigger one more, so they converge to equal shares.

  • UDP apps (video/audio) skip congestion control, so they can hog bandwidth; nobody polices it.
  • Parallel TCP connections: link R, 9 connections exist. New app with 1 TCP gets R/10. New app with 11 TCPs gets ≈ 11/20 ≈ R/2.

6. Evolution: fixing TCP’s weak spots

VariantProblem solvedIdea
Reno (limit)—Several losses in one window → cwnd halved for each (2 losses = ÷4), though one cut is enough.
NewRenoOver-cuttingOn 3 dup ACKs enter fast recovery. Partial ACK (covers only some packets outstanding at loss time) → don’t cut again, stay in recovery. Full ACK (covers all) → leave, enter congestion avoidance.
SACKMultiple losses per RTTACKs carry blocks of what was received, e.g. ACK 200, SACK 300-600. Sender sees exactly which segments are missing and resends only those, in one RTT. Congestion control rules are unchanged.
Example: SACKSender sends 100–599 in 100-byte segments; 200–299 is lost. Without SACK: three duplicate ACK 200s, and it can’t tell what else is missing. With SACK: ACK 200, SACK 300-400, then 300-500, 300-600 → sender knows only 200–299 is missing and resends just that.

QUIC (basis of HTTP/3)

  • Application-layer protocol on top of UDP (Chrome, YouTube, many Google servers).
  • Re-implements TCP-style connection setup, error control and congestion control, plus encryption, in user space.
  • Setup in 1 (or even 0) RTT with reliability, congestion control, authentication and encryption together.
  • Multiple streams in one connection, each with its own reliable delivery, so one lost packet doesn’t block the others (no head-of-line blocking). They share one congestion control.

7. Cheat sheet (memorise this)

One-liners • Transport = process-to-process; IP = host-to-host.
• UDP demux: 1 key (dest port). TCP demux: 4-tuple.
• UDP header: src port, dst port, length, checksum.
• Checksum: add 16-bit words, wrap the carry, flip bits.
• rdt tools: checksum (errors), ACK/NAK, seq # (duplicates), timer (loss), pipelining (speed).
• Utilization = (L/R) ÷ (RTT + L/R). GBN = cumulative ACK, resend all after the loss. SR = individual ACK, buffer, resend one. SR needs seq space ≥ 2 × window.
• TCP seq = number of the first byte; ACK = next byte expected.
• Est = 7/8 Est + 1/8 Sample. Dev = 3/4 Dev + 1/4 |Sample − Est|. Timeout = Est + 4 Dev.
• 3 dup ACKs = fast retransmit. rwnd = flow control (receiver). cwnd = congestion control (network). Window = min(cwnd, rwnd).
• Handshake: SYN → SYNACK → ACK. Close: FIN/ACK each way.
• Slow start ×2 per RTT → at ssthresh go +1 per RTT. 3 dup ACKs → halve. Timeout → cwnd = 1, ssthresh = half.
• Fair share = R/K. CUBIC = cubic growth near Wmax. BBR = keep the pipe just full. ECN = routers mark, no loss needed. SACK = say exactly what you got. QUIC = UDP + TCP features + streams.
