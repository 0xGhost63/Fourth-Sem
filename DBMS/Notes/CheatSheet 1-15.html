LECTURE 01 / 15

Database, DBMS, data and information

Start with the basic idea: an organisation has many related facts. A database keeps those facts together, while a DBMS is the software that manages them.

LEARN THE IDEASEE AN EXAMPLEREMEMBER THE EXAM POINT

1. What is a database?

A database is a shared collection of logically related data, plus a description of that data, designed to meet an organisation’s information needs.

Understand it

Think of a university: student records, courses, lecturers, enrolments, fees and results are connected. Keeping them in one organised collection makes it possible to answer questions such as ‘Which students are enrolled in Database Systems?’

Exam focus

Shared means authorised users can use the same data. Logically related means the facts belong to the same organisation or activity. Description of data means definitions such as table names, column names, data types and rules.

2. Database vs DBMS

The database is the data. The DBMS is the software that controls the data.

Understand it

A university database contains student and course records. MySQL, SQL Server or Oracle can act as the DBMS that stores, protects and retrieves those records.

Exam focus

Do not write that a database is software. The DBMS is software; the database is the organised data it manages.

3. Data, information and metadata

Data = raw facts. Information = useful meaning produced from facts. Metadata = data that describes other data.

Understand it

Marks 82, 76 and 91 are data. ‘The average is 83’ is information. ‘Marks is an integer column’ is metadata.

Exam focus

DDL defines structure and rules. DML reads or changes stored data. Controlled access includes security, integrity, concurrency control and recovery.

VISUAL SUMMARY
Database → DBMS → authorised users / applications. The DBMS is the controlled doorway between users and stored data.
60-SECOND RECAP

Database = collection; DBMS = manager; data = raw facts; information = meaningful result; metadata = description of data.

LECTURE 02 / 15

File processing systems vs DBMS

The central difference is where data is managed: separate files owned by individual programs, or shared data managed centrally by a DBMS.

LEARN THE IDEASEE AN EXAMPLEREMEMBER THE EXAM POINT

1. Traditional file processing

Each application keeps and manages its own files. Payroll has a payroll file; accounts has an accounts file; customer mailing has another file.

Understand it

If a customer changes address, the same address may need to be updated in three files. If one file is missed, the organisation has conflicting addresses.

Exam focus

Redundancy means duplicate copies. Inconsistency means those copies no longer agree.

2. Why file systems become difficult

Separate files create isolation, duplication, inconsistency and dependence between programs and file formats.

Understand it

If a program expects a field in a particular position, changing the file layout may force changes to the program. A new report may require a new program because the old one only answers fixed questions.

Exam focus

Remember the chain: separate files → repeated data → update problems → unreliable information.

3. How a DBMS improves the situation

A DBMS provides a shared central repository. Different applications access the same managed data through the DBMS.

Understand it

Sales, accounts and customer support can use the same customer record instead of maintaining independent copies.

Exam focus

Advantages: controlled redundancy, consistency, sharing, integrity, security, standards, productivity, concurrency, backup/recovery and easier maintenance. Disadvantages: complexity, cost, extra hardware, conversion cost, possible overhead and greater impact if a central system fails.

VISUAL SUMMARY
FILE SYSTEM: Payroll → payroll file; Accounts → accounts file; Sales → sales file.
DBMS APPROACH: Payroll / Accounts / Sales → DBMS → shared database.
60-SECOND RECAP

File system = separate program-owned files. DBMS = centrally managed shared data. Redundancy is duplication; inconsistency is disagreement.

LECTURE 03 / 15

Organising data and Data Flow Diagrams

Before designing a database, identify the things you store information about and understand how information moves through the organisation.

LEARN THE IDEASEE AN EXAMPLEREMEMBER THE EXAM POINT

1. Entity, attribute and relationship

Entity = the thing being described. Attribute = a fact about that thing. Relationship = how two things are connected.

Understand it

Customer is an entity. CustomerName and Address are attributes. ‘Customer places Order’ is a relationship.

Exam focus

Ask three questions: What thing? → entity. What details about it? → attributes. How are things connected? → relationship.

2. What a DFD shows

A Data Flow Diagram shows data entering a system, being processed, stored and sent out. It describes movement of data, not the order of program instructions.

Understand it

A customer sends Order Details to a process called Record Order. That process stores the order in an ORDER data store.

Exam focus

DFD symbols: external entity (outside person/system), process (transforms data), data flow (moving data), data store (saved data). Naming trick: entity = noun; process = verb phrase; flow = data name; store = noun.

3. DFD levels and how to build one

Context diagram shows the whole system as one process. Level 0 splits it into major processes. Level 1+ expands a process into smaller steps and detailed flows/stores.

Understand it

For a lemonade stand, the context diagram has one Lemonade System process connected to Customer, Employee and Vendor. Level 0 may split it into Sale, Production, Procurement and Payroll. Level 1 expands Sale into Record Order, Receive Payment and Sales Forecast.

Exam focus

Build it in order: list activities → context diagram → Level 0 → Level 1 or deeper → check DFD rules.

VISUAL SUMMARY
Context: [Customer] ⇄ (Lemonade System) ⇄ [Vendor]
Level 0: Lemonade System → Sale | Production | Procurement | Payroll
Level 1: Sale → Record Order → Receive Payment → Sales Forecast.
60-SECOND RECAP

Entity = thing; attribute = detail; relationship = connection. Context = one big process; Level 0 = main processes; Level 1 = detailed subprocesses.

LECTURE 04 / 15

Bus garage DFD, schema and subschemas

This lecture applies DFD thinking to a real process, then explains how a database can have one complete design but different user views.

LEARN THE IDEASEE AN EXAMPLEREMEMBER THE EXAM POINT

1. Bus garage repair case

A bus arrives for repair. A mechanic and helper record the problem, parts used, labour and total cost on a Shop Repair Order.

Understand it

The repair information is reused: Accounting bills the work, Inventory monitors parts, and the Supervisor reviews performance.

Exam focus

External entities include Bus, Mechanic, Helper, Supervisor, Inventory Management System and Accounting Department. Data stores include Personnel File, Repairs File, Bus Master List and Parts List.

2. Turn the story into a DFD

Find outside participants, the main process, smaller processes, data stores and the data passed between them.

Understand it

Main process: perform repairs and store repair information. Subprocesses: record bus ID/reason, determine parts, perform repair, calculate parts and total cost, record labour hours/cost.

Exam focus

Possible data flows: repair order, bus record, parts record, employee timecard and invoices. Keep process names as actions, e.g. ‘Calculate Total Cost’.

3. Schema and subschema

Schema = the complete logical description of the database. Subschema = a selected part of that design for a particular user or application.

Understand it

The full garage schema may include buses, repairs, employees, parts and invoices. The inventory application only needs the parts-related view; Accounting needs billing information.

Exam focus

A subschema is not a separate unrelated database. It is a user-specific view of the shared database structure.

VISUAL SUMMARY
EXTERNAL (user views) → CONCEPTUAL (complete logical design) → INTERNAL (physical storage) → physical database.
Different users see different external views of the same conceptual database.
60-SECOND RECAP

Schema = whole logical design. Subschema = relevant user view. External = user view; Conceptual = whole logical database; Internal = physical storage.

LECTURE 05 / 15

Data independence, DDL/DML and data models

A well-designed DBMS separates the way data is stored from the way users see and work with it.

LEARN THE IDEASEE AN EXAMPLEREMEMBER THE EXAM POINT

1. Three levels: quick recall

External describes what a particular user sees. Conceptual describes the complete logical database. Internal describes how data is physically stored.

Understand it

A cashier sees customer name and order total (external). The full logical design contains customers, orders and relationships (conceptual). Files and storage structures are internal.

Exam focus

Order: External → Conceptual → Internal. The physical database sits underneath the internal level.

2. Data independence

A change at a lower level should not force unnecessary changes at the level above it.

Understand it

Physical independence: change file organisation or add an index without changing the logical tables. Logical independence: change the conceptual design without breaking every existing user view.

Exam focus

Physical = internal change should not affect conceptual. Logical = conceptual change should not affect external views.

3. DDL, DML and data models

DDL defines or changes database structure. DML reads and changes stored data. A data model provides concepts for describing data, relationships and constraints.

Understand it

CREATE TABLE is DDL because it defines structure. SELECT, INSERT, UPDATE and DELETE are DML because they work with rows.

Exam focus

A data model has structural rules, allowed operations and integrity rules. Conceptual models describe what data exists (e.g. ER model); implementation models describe how it is represented (e.g. relational, hierarchical, network, object-oriented).

VISUAL SUMMARY
Physical independence: INTERNAL changes ─X→ CONCEPTUAL changes.
Logical independence: CONCEPTUAL changes ─X→ EXTERNAL views.
60-SECOND RECAP

DDL = define structure. DML = manipulate data. Physical independence protects the conceptual level; logical independence protects external views.

LECTURE 06 / 15

Hierarchical and network database models

Both models organise records using links. The key difference is how many parents a child/member can have.

LEARN THE IDEASEE AN EXAMPLEREMEMBER THE EXAM POINT

1. Hierarchical model

Data is arranged like a tree: one root, parent records and child records. One parent can have many children, but each child has only one parent.

Understand it

One bank account can have many transactions. The account is the parent; transactions are children.

Exam focus

It naturally supports 1:M relationships. Links between parent and child records use pointers.

2. Hierarchical strengths and limits

Its parent-child structure is easy to picture and can be efficient for fixed 1:M patterns.

Understand it

It becomes awkward when a record needs to belong to more than one parent. Pointer-based navigation can also make programs complex.

Exam focus

Slide-listed strengths include simple parent-child organisation, uniform security, integrity and efficiency for repeated 1:M data. Limits include design complexity, limited relationship flexibility and lack of structural independence.

3. Network model

The network model extends the tree idea. A member record can have multiple owners/parents, so it can represent more complex connections.

Understand it

A student may be connected to several courses, and each course may have many students. This is not a simple one-parent tree.

Exam focus

The slides describe owner records, member records and sets that define their relationships. The hierarchical model is a subset of the network model.

VISUAL SUMMARY
HIERARCHICAL: Account → Transaction A / Transaction B / Transaction C. Each transaction has one parent.
NETWORK: Course A ↔ Student 1; Course B ↔ Student 1. A member can have multiple owners.
60-SECOND RECAP

Hierarchical = tree; one parent per child. Network = more flexible links; a member can have multiple parents/owners.

LECTURE 07 / 15

Object-oriented and relational database models

The object model stores data as objects. The relational model presents data as tables connected through keys.

LEARN THE IDEASEE AN EXAMPLEREMEMBER THE EXAM POINT

1. Object-oriented database model

An object is an instance of a class. A class groups the data fields and operations for a kind of object.

Understand it

A Clerk class may contain name, address, ID and salary, plus operations such as get_name() or annual_salary(). Objects can contain nested objects and arrays.

Exam focus

The slide-listed advantages are real-world modelling, model simplicity and reduced data size. The listed disadvantages include lack of SQL query language and lack of automatic constraints.

2. Relational database model

A relational database is a collection of tables. Each table has rows and columns; common key values connect related tables.

Understand it

STUDENT(StudentID, Name) and COURSE(CourseID, Title) can be linked through an ENROLLMENT table containing StudentID and CourseID.

Exam focus

Relational terms: relation = table; tuple = row; attribute = column; domain = allowed values for a column.

3. Why relational databases became useful

Tables are conceptually simple, users do not need to know the physical access path, and SQL allows ad hoc queries.

Understand it

A user can ask a new question with a SELECT query instead of requiring a programmer to build a new report application.

Exam focus

Slide-listed disadvantages include resource requirements, the possibility of poor design, and isolated pockets of information if databases are not integrated.

VISUAL SUMMARY
OBJECT: Class → Object (data fields + operations).
RELATIONAL: STUDENT table + COURSE table + ENROLLMENT table (keys connect them).
60-SECOND RECAP

Hierarchical = tree; Network = multi-parent links; Object-oriented = objects/classes; Relational = tables/rows/columns.

LECTURE 08 / 15

DBMS functions, architecture and metadata

A DBMS does much more than save records: it processes queries, checks permissions, coordinates users, manages storage and recovers after failures.

LEARN THE IDEASEE AN EXAMPLEREMEMBER THE EXAM POINT

1. Main DBMS responsibilities

A DBMS stores, retrieves and updates data; provides a catalog; supports transactions; manages concurrent users; enforces security and integrity; and provides recovery and utility services.

Understand it

If two users update records at the same time, concurrency control helps prevent their operations from interfering incorrectly. If a failure occurs, recovery services help restore the database.

Exam focus

Learn the jobs as groups: data handling, user/catalog services, transaction/concurrency, security/integrity, backup/recovery and data independence.

2. DBMS components: what each does

The query processor handles commands; optimizer chooses an efficient execution plan; authorization checks permissions; integrity checker checks rules; transaction manager coordinates transactions; scheduler manages concurrent work.

Understand it

The buffer manager transfers data between main memory and secondary storage. The recovery manager helps restore after failure. The dictionary manager manages metadata; file manager/access methods access stored records.

Exam focus

Exam trick: if asked ‘which component?’, match the action word: permission → authorization; faster plan → optimizer; simultaneous operations → scheduler; failure → recovery; memory/storage transfer → buffer manager.

3. Metadata and system catalog

Metadata is information describing the database. The system catalog (data dictionary) stores this description.

Understand it

Technical metadata includes table names, data types, keys, indexes and constraints. Business metadata includes ownership, policies and business rules. Descriptive metadata can include title, author and date. The slides also list operational metadata.

Exam focus

Metadata describes data; the system catalog stores metadata. Do not confuse the catalog with the actual business records.

VISUAL SUMMARY
Query → command/query processing → authorization + integrity checks → optimisation → transaction/scheduling → buffer/file access → result. Recovery manager supports failure recovery.
60-SECOND RECAP

Authorization = permission; optimizer = efficient plan; scheduler = concurrent work; buffer = memory/storage transfer; recovery = restore; catalog = metadata.

LECTURE 09 / 15

Relational model, keys and constraints

A relational database stores data in relations (tables). Keys identify rows and help connect tables.

LEARN THE IDEASEE AN EXAMPLEREMEMBER THE EXAM POINT

1. How to read a relation

A relation is a table. A tuple is a row. An attribute is a column. A domain is the set of allowed values for an attribute.

Understand it

In STUDENT(StudentID, Name, Age), one student's record is a tuple; StudentID is an attribute; Age might have a domain of positive integers.

Exam focus

Cardinality of a relation = number of rows. Degree of a relation = number of columns. This is a common exam trap.

2. Properties of a relation

Each relation has a distinct name; each cell contains one atomic value; column names are distinct; values in a column come from the same domain; duplicate rows are not allowed; row/column order does not matter.

Understand it

Do not store ‘0300, 0311’ as two phone numbers in one cell if the design requires atomic values. Store separate values/records instead.

Exam focus

Atomic = one value per cell. Relation cardinality = rows; degree = columns.

3. Understand the key family

A super key uniquely identifies a row. A candidate key is a minimal super key. A primary key is the candidate key selected as the main identifier. A composite key uses multiple attributes. A surrogate key is an artificial generated identifier.

Understand it

StudentID may be a candidate key. StudentID + Name is also unique, but not minimal, so it is a super key rather than a candidate key. In ENROLLMENT, (StudentID, CourseID) can be a composite key.

Exam focus

Every candidate key is a super key, but not every super key is a candidate key. Choose stable identifiers. A surrogate key is convenient but has no business meaning and does not itself prevent duplicate real-world records.

VISUAL SUMMARY
STUDENT table: StudentID | Name | Age. Rows = tuples. Columns = attributes.
Key path: Super key → minimal one = Candidate key → selected one = Primary key.
60-SECOND RECAP

Cardinality = rows; degree = columns. Candidate key = minimal super key. Primary key = chosen candidate key. Composite = multiple columns. Surrogate = artificial ID.

LECTURE 10 / 15

Relational integrity and SQL constraints

Constraints are rules that stop invalid data from entering a table. Integrity rules protect correctness within a table and between related tables.

LEARN THE IDEASEE AN EXAMPLEREMEMBER THE EXAM POINT

1. Three integrity ideas

Entity integrity: a primary key cannot be NULL. Referential integrity: a foreign key must match a referenced candidate key, unless NULL is allowed. Enterprise constraints: additional rules set by the organisation.

Understand it

Every order must have its own OrderID. If an order stores PersonID=25, Person 25 must exist in PERSON unless the relationship is optional and NULL is permitted.

Exam focus

Primary key identifies a row. Foreign key connects a row to another table.

2. SQL constraints you must recognise

NOT NULL requires a value. UNIQUE prevents duplicate values. PRIMARY KEY is unique and non-NULL. FOREIGN KEY checks a reference. CHECK tests a condition. DEFAULT supplies a value when omitted.

Understand it

Age INT CHECK (Age >= 18) rejects ages below 18. City VARCHAR(50) DEFAULT 'Lahore' supplies Lahore if no city is entered.

Exam focus

INDEX helps retrieval but is not an integrity constraint in the same sense as PK/FK/CHECK.

3. Parent and child tables

The referenced table is the parent. The table holding the foreign key is the child. Many child rows can refer to the same parent row.

Understand it

PERSON(PersonID PK) ← ORDERS(PersonID FK). Ten orders may all refer to the same PersonID. Therefore a foreign key is not usually unique.

Exam focus

Referenced column must be a candidate key (such as a primary key or unique key). A foreign key does not automatically have to be unique.

VISUAL SUMMARY
PERSON (PersonID PK) 1 ─────< M ORDERS (OrderID PK, PersonID FK). Many orders can belong to one person.
60-SECOND RECAP

PK = unique + NOT NULL. FK = valid reference. FK is usually allowed to repeat. CHECK = condition. DEFAULT = fallback value.

LECTURE 11 / 15

SQL views and indexes

A view is a saved way to look at data. An index is a faster lookup structure. They solve different problems.

LEARN THE IDEASEE AN EXAMPLEREMEMBER THE EXAM POINT

1. Views

A normal view is a virtual relation derived from one or more base tables. It stores the view definition, not a separate copy of the result rows.

Understand it

A BrazilCustomers view can show only CustomerName and ContactName for customers whose Country is Brazil. Users query the view as if it were a table.

Exam focus

Views can hide selected data, customise user access, simplify joins/queries, support external schemas and help logical data independence.

2. Types of views

Simple view: usually one base table. Complex view: multiple tables, joins, expressions or grouping. Inline view: a SELECT subquery in FROM. Materialized view: stores the result physically.

Understand it

A materialized view can make repeated retrieval faster, but its stored result must be kept in sync with changes to the base tables.

Exam focus

Normal view = definition, result generated when queried. Materialized view = stored result.

3. Indexes

An index gives the DBMS a quicker path to find rows, often reducing disk input/output for searches.

Understand it

An index on LastName can help find customers by surname without scanning every row.

Exam focus

Trade-off: indexes can speed up SELECT/WHERE retrieval but add work to INSERT/UPDATE. Clustered index defines the physical row order (one per table); non-clustered index is separate and points to rows (multiple possible).

VISUAL SUMMARY
BASE TABLES → VIEW (custom result for a user).
TABLE DATA + INDEX (lookup structure) → faster row location; extra maintenance on writes.
60-SECOND RECAP

View = customised virtual result. Materialized view = stored result. Index = lookup accelerator. Clustered = physical order; non-clustered = separate structure.

LECTURE 12 / 15

Conceptual schema design and relationships

Database design begins with user requirements, turns them into an ER model, then refines and implements that design.

LEARN THE IDEASEE AN EXAMPLEREMEMBER THE EXAM POINT

1. Database design sequence

Requirements analysis → conceptual design → schema refinement → logical design → user interface design → physical design → security design.

Understand it

First discover what users need. Then draw a high-level ER model. Refine it (including normalisation). Convert it to the DBMS model, design views/interfaces, decide storage/indexes and plan access control.

Exam focus

Do not start by choosing indexes before understanding the data and relationships.

2. Entity sets and relationship degree

An entity set is a collection of similar entities sharing the same kind of attributes. A relationship connects participating entity sets.

Understand it

‘Employee works in Department’ connects Employee and Department. Unary relates an entity set to itself; binary connects two sets; ternary connects three sets together.

Exam focus

Unary: Employee supervises Employee. Binary: Student enrols in Course. Ternary: Employee works for a Department at a Location.

3. Cardinality and participation

Cardinality tells how many entities can be related. Participation tells whether participation is optional or compulsory.

Understand it

1:M: one department offers many courses. M:N: many students take many modules. Optional/partial: a course may exist before any student enrols. Mandatory/total: every weak entity must be related to its owner.

Exam focus

Read cardinality in both directions. Ask ‘for one A, how many B?’ and ‘for one B, how many A?’ Double line in the slides represents total participation.

VISUAL SUMMARY
DEPARTMENT 1 ─────< M COURSE.
STUDENT M >────< M COURSE (many-to-many).
Unary = 1 entity set; Binary = 2; Ternary = 3.
60-SECOND RECAP

Cardinality = how many. Participation = optional or mandatory. Relationship degree = number of participating entity sets.

LECTURE 13 / 15

Attribute types, weak entities and entity vs attribute

This lecture teaches how to describe entities correctly and how to model something that cannot be identified on its own.

LEARN THE IDEASEE AN EXAMPLEREMEMBER THE EXAM POINT

1. Attribute types

Simple cannot be meaningfully divided. Composite has meaningful parts. Single-valued has one value per entity. Multi-valued can have several. Derived is calculated from other attributes. Key identifies an entity uniquely.

Understand it

Age is simple; Address may be composite (street, city, postcode); date of birth is single-valued; phone numbers may be multi-valued; age can be derived from date of birth; StudentID is a key.

Exam focus

Do not confuse the pairs: simple/composite asks ‘can it be split?’; single/multi asks ‘how many values?’ These are two different questions.

2. Strong vs weak entity

A strong entity has its own primary key. A weak entity cannot be uniquely identified using only its own attributes; it needs the owner’s key plus a partial key.

Understand it

An Employee may have several Dependents. DependentName alone may repeat across employees. EmployeeSSN + DependentName can identify a dependent.

Exam focus

Weak entity has total participation in its identifying relationship and depends on an owner. The slides show ON DELETE CASCADE as a possible way to remove dependent records when the owner is deleted.

3. Entity or attribute?

An entity can have its own attributes and relationships. An attribute is a descriptive value belonging to one entity.

Understand it

Product, Supplier and Address can be entities when they have their own details or relationships. Description, Price, PhoneNumber, Street, City and Postcode are attributes in the example.

Exam focus

Make it an entity when it needs its own identity, has its own attributes, participates in relationships or can occur multiple times. Otherwise it may be an attribute.

VISUAL SUMMARY
EMPLOYEE (strong entity, SSN) 1 ─────< M DEPENDENT (weak entity).
Dependent key = EmployeeSSN + DependentName.
60-SECOND RECAP

Simple/composite = parts. Single/multi = number of values. Derived = calculated. Weak entity = owner key + partial key.

LECTURE 14 / 15

How to build an Entity Relationship Diagram

An ERD converts a written description into a picture of entities, their attributes and the relationships between them.

LEARN THE IDEASEE AN EXAMPLEREMEMBER THE EXAM POINT

1. Learn the symbols

Rectangle = entity. Oval = attribute. Underlined attribute = key. Diamond = relationship. Double oval = multi-valued attribute. Dashed oval = derived attribute. Double rectangle = weak entity. Double diamond = identifying relationship. Double line = total participation.

Understand it

If the question asks you to draw an ERD, use consistent symbols and label relationships with meaningful verbs.

Exam focus

Entity = rectangle; relationship = diamond; attribute = oval. Memorise these before attempting a full diagram.

2. Worked university example: find entities and relationships

Read the story and identify nouns that represent things with their own identity. Then identify verbs that connect them.

Understand it

Entities: Department, Course, Module, Lecturer, Student. Relationships: Department offers Course; Course includes Module; Student enrols in Course; Student takes Module; Lecturer teaches Module; Department employs Lecturer; Lecturer tutors Student.

Exam focus

Nouns are candidates for entities, not automatic entities. Check whether they have their own identity/details. Verbs are candidates for relationships.

3. Decide cardinalities and verify

Use exact wording to decide the ratios. ‘Each department offers several courses’ suggests Department 1:M Course. ‘Students take modules’ can be M:N if many students take many modules.

Understand it

A student enrols in a particular course in the simplified example: one course may have many students, while each student is assigned to one course. Always follow the problem statement rather than guessing.

Exam focus

Final workflow: entities → attributes → keys → relationships → cardinalities → participation → draw → check every sentence against the ERD.

VISUAL SUMMARY
University ERD skeleton: Department —offers— Course —includes— Module; Student —enrols in— Course; Student —takes— Module; Lecturer —teaches— Module; Department —employs— Lecturer; Lecturer —tutors— Student.
60-SECOND RECAP

Nouns suggest entities; descriptive facts suggest attributes; verbs suggest relationships. Cardinalities come from the exact wording.

LECTURE 15 / 15

Entity classification and ERD refinement

After drawing an ERD, review whether the entities are necessary, whether any relationships are redundant and how M:N relationships become tables.

LEARN THE IDEASEE AN EXAMPLEREMEMBER THE EXAM POINT

1. Re-check entity vs attribute

Both entities and attributes can appear as nouns. The decision depends on what the information represents, not grammar alone.

Understand it

Product has Description and Price. Supplier has Name and Phone. Address can be an entity when Street, City and Postcode are separate details or when addresses need their own relationships.

Exam focus

Entities can have attributes and relationships. An attribute belongs to one entity and is usually a descriptive value.

2. Redundant 1:1 relationships

A 1:1 relationship may be redundant if every entity on both sides participates and the two concepts do not need separate identities/lifecycles.

Understand it

If every Supplier has exactly one Address and every Address belongs to exactly one Supplier, the design may merge Supplier and Address into one entity with all attributes.

Exam focus

Do not merge every 1:1 pair automatically. Check whether participation is total on both sides and whether the concepts truly belong together.

3. Resolve many-to-many relationships

When converting an M:N relationship into relational tables, create an associative entity (junction table) containing the keys of both entities and any attributes of the relationship.

Understand it

STUDENT and COURSE are M:N. Create ENROLLMENT(StudentID, CourseID, EnrollmentDate, Grade). StudentID + CourseID can form the composite primary key; each column is also a foreign key.

Exam focus

Result: STUDENT 1:M ENROLLMENT and COURSE 1:M ENROLLMENT. The associative table turns one M:N relationship into two 1:M relationships.

4. Transactional and component entities

Transactional entities contain measurements that can be summarised, such as quantity and amount in a sale. Component entities describe who, what, where, when or why an event happened.

Understand it

For a sale: Customer = who, Product = what, Location = where, Period = when. Sale itself can be a transaction with quantity and amount.

Exam focus

A transaction records an event; components describe the context of that event.

ACTIVE RECALL

Test yourself before the exam

Try answering before opening each answer.

1. What is the difference between a database and a DBMS?

A database is the organised collection of related data. A DBMS is the software used to define, create, maintain and control access to it.

2. Give one example of redundancy causing inconsistency.

A customer's address is stored in three files. If only two are updated, the copies disagree.

3. What is the difference between an entity and an attribute?

An entity is the thing being described; an attribute is one of its properties.

4. What does each DFD level show?

Context = whole system as one process; Level 0 = major processes; Level 1+ = detailed subprocesses, flows and stores.

5. Distinguish schema from subschema.

Schema is the complete logical database description; a subschema is the part relevant to a particular user/application.

6. Logical vs physical data independence?

Logical protects external views from conceptual changes; physical protects the conceptual schema from internal storage changes.

7. What is the main limitation of a hierarchical model?

A child has only one parent, so it is limited for relationships where a record needs multiple parents.

8. Define relation cardinality and degree.

Cardinality is the number of rows; degree is the number of columns.

9. Why is every candidate key a super key but not vice versa?

A candidate key uniquely identifies a row and is minimal. A super key may contain unnecessary extra attributes.

10. Does a foreign key have to be unique?

Usually no. Many child rows can refer to the same parent row.

11. What is the difference between a view and an index?

A view presents a derived/customised result. An index helps locate rows faster.

12. What does a weak entity need to be identified?

The owner's primary key plus the weak entity's partial key.

13. How do you resolve an M:N relationship into tables?

Create an associative/junction table with both entity keys and any relationship attributes.

14. When might a 1:1 relationship be redundant?

When participation is total on both sides and the two entities can sensibly be merged.

15. How do you identify entities and relationships in a written problem?

Nouns suggest candidate entities; descriptive facts suggest attributes; verbs suggest relationships. Verify each using the exact requirements.
